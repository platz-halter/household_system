## Commands

```bash
cp .env.example .env                                     # POSTGRES_PASSWORD must be alphanumeric (special chars break the DSN)
docker compose up --build                                # postgres + auth only (always on)
docker compose --profile storage up --build              # + storage backend & frontend
docker compose --profile household --profile storage up --build
docker compose --profile storage down                    # --profile must come BEFORE the subcommand

uv sync                                                  # install workspace + dev deps (ruff, pytest)
uv run ruff check . && uv run ruff format .
```

Ports published to localhost: postgres `5432`, auth `8001`, household-backend `8002`, storage-backend `8003`, storage-frontend `8080`.

There is no test suite in the repo yet. pytest, pytest-asyncio and httpx are in the root `dev` dependency group, so new tests can use them.

### Migrations (per service, run from the repo root)

```bash
export DATABASE_URL="postgresql+asyncpg://<POSTGRES_USER>:<POSTGRES_PASSWORD>@localhost:5432/storage"
uv run --package storage-backend alembic -c storage/backend/alembic.ini revision --autogenerate -m "msg"
uv run --package storage-backend alembic -c storage/backend/alembic.ini upgrade head
uv run --package storage-backend alembic -c storage/backend/alembic.ini check   # fails if models ≠ migrations
```

For the other services, swap in `auth`/`household`, use `--package auth` or `household-backend` (check that service's `pyproject.toml` for the name), and point `-c` at its `alembic.ini`. Alembic refuses to run when `DATABASE_URL` is unset, so it can never fall back to the default DB. Always review autogenerated files, because renames show up as drop+add and new NOT NULL columns need a `server_default`. Never edit a migration that has already been applied.

## Architecture

**uv workspace monorepo** (`pyproject.toml` at the root). Members: `shared`, `auth`, `household/backend`, `storage/backend`. All backends are async FastAPI + SQLAlchemy 2.0 (asyncpg), Python 3.12.

**One Postgres container, one database per service** (`auth`, `household`, `storage`, created by `postgres/init/01-create-databases.sh`). `docker-compose.yml` builds each service's `DATABASE_URL` and hardcodes those DB names. The `*_DB_NAME` variables in `.env.example` are not used.

**Compose profiles:** `postgres` and `auth` have no profile and always start. `household-backend` sits behind the `household` profile; `storage-backend` and `storage-frontend` sit behind the `storage` profile. All backend Dockerfiles use the **repo root as build context**, so they can copy `shared/` and `uv.lock`.

**`shared` package**: write this code once here; don't copy it into each service.

- `config.py`: one pydantic `Settings` class read from env, used by every service.
- `db.py`: async engine, the `get_db` dependency, and a single `Base`. Each service imports only its own models, so each service's metadata and autogenerate see only its own tables.
- `auth.py`: token verification. **Both auth paths are always active, and the choice is made per token from its JWT `alg` header**: HS256 means a local token (signed by the `auth` service with `LOCAL_JWT_SECRET`), and RS256 means an Authentik token (checked against JWKS, with audience = `AUTHENTIK_CLIENT_ID`). There is no global mode switch. Services only call `Depends(require_role("admin", "user"))` and get back a `CurrentUser(subject, role, source)`.
- `migrations.py`: the shared Alembic env logic. Each service's `migrations/env.py` just imports its models and calls `run_migrations(Base.metadata)`.
- `entrypoint.sh`: the container CMD for every backend. It runs `alembic upgrade head`, then `uvicorn`. **Schema changes happen only through migrations**, because the apps never call `create_all`.
- `__init__.py`: just `__version__` — the single source of truth for the app version, surfaced in every service's `GET /health` and OpenAPI `info.version`, and in both frontends' Settings footer (`js/version.js`, kept in sync by hand — no build step reads one from the other). Bump this, the five `pyproject.toml` `version` fields, and both `version.js` files together on a real release.

**Roles:** `admin` / `user` / `viewer`. Authentik groups map to roles via the admin-editable `admin_group`/`user_group`/`viewer_group` settings (default `household-system-{admins,users,viewers}`; see the auth service entry below) — not a hardcoded dict. **Explicit allow-list, not fail-open-to-viewer**: a validly-signed Authentik token whose `groups` claim contains none of the three configured names is rejected outright (401 from `_verify_authentik_token`), not downgraded to `viewer` — being a real user on a shared Authentik instance that also serves other homelab services is not by itself a reason to get into this one. (This was originally fail-closed-to-viewer; changed after a real homelab's Authentik instance made the gap concrete — anyone with e.g. `svc-omada-admins` or `svc-proxmox-admins` and nothing household-related could otherwise log in as a viewer.) Viewers are read-only. **Storage has no admin/user distinction at all** — deliberate, not unfinished; nothing in that domain needs gatekeeping beyond logged-in-vs-viewer. **Household gates 7 routes to admin-only** (`can_admin = require_role("admin")` in its `main.py`): weekly goal/money-rate/reminder-schedule settings, running the balancer on demand, generating/marking-paid a report, and the Authentik connection panel. Both frontends' `js/auth.js` also read this dynamically now (`warmGroupRoleMap()`, fired-and-forgotten at boot, never awaited — an unreachable auth service must not delay the first render) — renaming a group through the panel needs no frontend edit or rebuild either. This used to be a hardcoded, manually-synced mirror; that caused a real production incident (an admin's own renamed Authentik group left them stuck on `viewer` client-side, including blocked from `/admin` by the router's own guard, even though the backend was already authorizing them correctly — traced by decoding their token in the browser console and confirming the backend accepted it directly via `fetch`) before it was made dynamic.

**auth service:** local-account fallback. `POST /token` (OAuth2 form login, returns an HS256 JWT with a `role` claim; rate-limited per-username by `auth_service/rate_limit.py` after 5 failures/15min, not per-IP — see that module's docstring for why), `POST /bootstrap-admin` (unauthenticated, only works while there are no users), and `POST /users` (admin only). Also owns the live Authentik connection config: `GET /authentik-config` is public (the issuer/JWKS/client-id/group-names/etc. values aren't secret — they're already visible in every OIDC redirect), falling back to `shared/config.py`'s env-sourced defaults until an admin saves an override. This now includes `admin_group`/`user_group`/`viewer_group` (which Authentik group name maps to which app role — a hardcoded dict before this), so `shared/auth.py` no longer has a `GROUP_ROLE_MAP` constant; `_role_from_groups` reads these three the same cached-and-polled way as the other seven fields. `PUT`/`POST /authentik-config/reset` are admin-only **and** additionally require a local admin's username+password in the request body — whoever can repoint `issuer`/`jwks_url`/the group names controls who every service trusts as an admin, so a currently-valid bearer token alone isn't enough. `PUT` also rejects non-distinct group names (reusing one across two roles would make the higher one unreachable, not shared). Every service (household/storage backends, and auth itself, over its own `auth:8000` alias) polls this through `shared/auth.py`'s `_AuthentikConfigCache` (60s TTL) instead of reading `Settings` directly, so a saved change reaches token verification everywhere without a restart — **except** both frontends' `ROLE_FROM_GROUPS` in `js/auth.js`, which is still a hardcoded, manually-synced, UI-display-only mirror (never used for actual authorization) and still needs a source edit + rebuild if you rename a group and want the UI to agree with what the backend now enforces.

**storage service:**

- Backend: routes are in `main.py`, query logic in `crud.py`, Pydantic I/O models in `schemas.py`. The `/items/bulk*` routes must stay declared **before** `/items/{item_id}`, or FastAPI matches the wrong route.
- Images are stored in the `storage-images` volume at `/app/data/images`, and serving them requires auth.
- Baseline migrations are written as idempotent "create if not exists", so databases created before Alembic adopt the schema cleanly.

**household service:** the full chores/points domain from `PROJECT_SPEC.md` is built — `Task`/`TodoItem`/`PointsEntry`/`Category`, the auto-balancer (`household_service/balancing.py`'s pure `balance()`/`rebalance()`, invoked from `crud.run_balancing`), web push, PDF reports, points→money conversion. See `PROJECT_STATE.md` for the full feature-by-feature status.

- **Chained tasks**: a `Task` can declare `TaskChainLink`s — "when I'm completed, also spawn these onto the board as one-off `TodoItem`s." Trigger is **completion**, not scheduling (`crud.complete_task`/`complete_todo`, via `crud._spawn_chain_children`), so a child only ever gets an instance when its parent actually happened. `same_user=True` assigns the spawned todo directly to the completer; `same_user=False` assigns it immediately through the same fairness logic the balancer's sweep uses (`crud._assign_chain_todo_now`, sharing `crud._gather_balancer_load` with `run_balancing`), always excluding the completer. A task reachable only as someone's chain child (`crud.is_chain_child`/`chain_child_task_ids`, derived live from `task_chain_links` — never a stored flag) has exactly one source of instances: excluded from `run_balancing`'s sweep, and `complete_task` rejects completing it directly (409) — its points only come from completing the spawned todo. Chains can run multiple levels deep; `crud.create_chain_link` rejects a link that would close a cycle.
- **On-break AND viewer exclusion from assignment**: `crud._check_assignable` rejects handing work to an on-break user (400) — used by todo create/update, the admin reassign, and takeover-request creation. The balancer's sweep/rebalance and the chain-task auto-assigner build their own `eligible` list via `crud._is_eligible_for_tasks` (not `_check_assignable`, since there's no single user to reject — it's filtering a whole household), which excludes both `on_break` **and** `role == "viewer"` — a viewer can never complete anything themselves (`can_write`-gated), so handing one a balancer-swept task or chain-spawned todo just leaves it permanently stuck. If `_is_eligible_for_tasks` finds nobody, the item is left unassigned, same as any other "nobody eligible" case.
- **Reassign vs. takeover request, UI clarity**: both the Board's admin-only reassign button (`icons.swap`) and the "ask to take over" button (`icons.send`, `household/frontend/js/takeover.js`) are deliberately distinct icons with explanatory tooltips — they're easy to conflate since both end with "someone else holds it now." Any writable user (not just admin) can ask to take over something THEY currently hold, from either Home or the Board (`takeover.js`'s `takeoverControl()` is shared between both pages). `household/frontend/js/taskPicker.js` (search + category-filter popup, also shared — originally board.js's "From task" picker) is what backs the Tasks page's chain-task child selector too, replacing a native `<select>` that would otherwise flood with every task in the household — **picking a task in that popup immediately performs the action** (adds the chain link / prefills the todo form, depending on caller), on purpose: an earlier two-step "pick, then press a separate Add button" version let a user pick a chain task, then press the Edit Task modal's main Save button assuming the pick was already part of what got saved — it wasn't, and nothing told them so.
- **Notification inbox**: the bell icon next to Settings in the topbar (`household/frontend/index.html`, wired from `household/frontend/js/notifications.js`) is a persistent, checkable inbox on top of the one-shot Web Push notifications this app already sends — currently surfaces incoming takeover requests only, each actionable (Accept/Decline) right from the panel. Polls `GET /takeover-requests?direction=incoming` every 30s for the badge count; every page that can also resolve a takeover request (Home, the panel itself) calls `refreshNotificationBadge()` after doing so rather than waiting for the next poll. Hidden for a viewer or before login — `refreshNotificationBadge()` re-checks role on every call (not just once at boot), since local login (`login.js`) is an in-SPA `navigate()`, not a real page reload, so there's no second `main.js` boot to re-evaluate who's logged in.
- **Completing a chain-child task directly** (`force` on `TaskCompleteRequest`): `crud.complete_task` rejects this by default (409) unless `force=True`, which bypasses *only* that one check — everything else (the `times_per_day` cap, ramp-up, chain-spawning the task's own further children) still applies. The frontend only ever sends `force: true` after a confirm dialog naming which task(s) chain it (`GET /tasks/{id}/chain-parents`, the reverse of `/chain-links` — `crud.list_chain_parents`/`ChainParentOut`). Deliberately doesn't touch any already-spawned, still-open todo for the same chain link — which one(s) to cancel is ambiguous when more than one occurrence could legitimately be outstanding, so that judgment call is left to the person confirming, same as `times_per_day` already does.
- **Admin reassign vs. takeover requests**: two different ways an assignment changes hands, both only for board `TodoItem`s (not recurring `TaskAssignment`s, except takeover requests which cover both). `POST /todos/{id}/reassign` (`can_admin`) is instant, no consent needed (`crud.reassign_todo`) — still respects a chain todo's `exclude_user_id`. A takeover request (`can_write` — any writable user, not just admin) is consent-based: `TakeoverRequest` (new table, `todo_item_id`/`task_assignment_id` — exactly one set, enforced by a `CheckConstraint`; only one *pending* request per item, enforced by two partial unique indexes since a plain composite unique index can't do it — NULL-vs-NULL is never a duplicate in SQL) sits in `pending` until the target accepts or declines, or the requester cancels. `accept_takeover_request` re-validates the requester still holds the item with a conditional `UPDATE` (same race-safety pattern as `claim_todo`) before moving it, and stamps `TaskAssignment.reassigned_at` so the balancer's rebalance pass won't immediately pull an accepted assignment back. Going on break, an admin reassign, or the balancer's rebalance pass all cancel whatever pending takeover request they just made stale.

## Frontend conventions (`storage/frontend`, and future `household/frontend`)

- Vanilla HTML/CSS/JS with native ES modules and **no build step or framework**. This is a deliberate project goal: keep it maintainable by someone who isn't primarily a web developer. It's served by nginx.
- Clean path-based routing lives in `js/router.js` (`/overview`, `/settings`, `/login`, etc.) — `history.pushState`/`replaceState` + a `popstate` listener, plus a document-level click interceptor that turns a click on an internal `<a href="/...">` into client-side navigation instead of a full page load. nginx's existing SPA fallback (`try_files $uri $uri/ /index.html;`) serves `index.html` for every route on a direct load/refresh. Both `index.html` files load their CSS/JS via root-absolute paths (`/css/...`, `/js/main.js`) specifically so this keeps working from a deep route, not just `/`.
- `js/config.js` holds the backend base URLs. In production they are the same-origin `/api/auth` and `/api/storage` paths, proxied by Caddy, which strips the prefix. During local dev they currently point straight at `127.0.0.1:8001`/`8003`.
- All API calls go through `js/api.js`. It attaches the bearer token, retries once after an Authentik refresh-token exchange on a 401, and shows toasts on errors. Images have to load through `fetchImageUrl()` (a blob URL), because `<img src>` can't send an auth header. Call `invalidateImageUrl()` after a re-upload.
- `js/auth.js` handles Authentik OIDC (Authorization Code + PKCE, public client) plus local login. For UI role gating, use `getCurrentUserInfo()`, not `decodeToken().role`: Authentik tokens carry `groups`, not `role`.
- Use `confirmDialog.js` instead of native `confirm()`.
- Theming uses CSS custom properties in `css/tokens.css` plus the `THEMES` registry in `js/theme.js`.
