## Commands

```bash
cp .env.example .env                                     # POSTGRES_PASSWORD must be alphanumeric (special chars break the DSN)
docker compose up --build                                # postgres + auth only (always on)
docker compose --profile storage up --build              # + storage backend & frontend
docker compose --profile household --profile storage up --build
docker compose --profile storage down                    # --profile must come BEFORE the subcommand

uv sync                                                  # install workspace + dev deps (ruff, pytest)
uv run ruff check . && uv run ruff format .
```

Ports published to localhost: postgres `5432`, auth `8001`, household-backend `8002`, storage-backend `8003`, storage-frontend `8080`.

There is no test suite in the repo yet. pytest, pytest-asyncio and httpx are in the root `dev` dependency group, so new tests can use them.

### Migrations (per service, run from the repo root)

```bash
export DATABASE_URL="postgresql+asyncpg://<POSTGRES_USER>:<POSTGRES_PASSWORD>@localhost:5432/storage"
uv run --package storage-backend alembic -c storage/backend/alembic.ini revision --autogenerate -m "msg"
uv run --package storage-backend alembic -c storage/backend/alembic.ini upgrade head
uv run --package storage-backend alembic -c storage/backend/alembic.ini check   # fails if models ≠ migrations
```

For the other services, swap in `auth`/`household`, use `--package auth` or `household-backend` (check that service's `pyproject.toml` for the name), and point `-c` at its `alembic.ini`. Alembic refuses to run when `DATABASE_URL` is unset, so it can never fall back to the default DB. Always review autogenerated files, because renames show up as drop+add and new NOT NULL columns need a `server_default`. Never edit a migration that has already been applied.

## Architecture

**uv workspace monorepo** (`pyproject.toml` at the root). Members: `shared`, `auth`, `household/backend`, `storage/backend`. All backends are async FastAPI + SQLAlchemy 2.0 (asyncpg), Python 3.12.

**One Postgres container, one database per service** (`auth`, `household`, `storage`, created by `postgres/init/01-create-databases.sh`). `docker-compose.yml` builds each service's `DATABASE_URL` and hardcodes those DB names. The `*_DB_NAME` variables in `.env.example` are not used.

**Compose profiles:** `postgres` and `auth` have no profile and always start. `household-backend` sits behind the `household` profile; `storage-backend` and `storage-frontend` sit behind the `storage` profile. All backend Dockerfiles use the **repo root as build context**, so they can copy `shared/` and `uv.lock`.

**`shared` package**: write this code once here; don't copy it into each service.

- `config.py`: one pydantic `Settings` class read from env, used by every service.
- `db.py`: async engine, the `get_db` dependency, and a single `Base`. Each service imports only its own models, so each service's metadata and autogenerate see only its own tables.
- `auth.py`: token verification. **Both auth paths are always active, and the choice is made per token from its JWT `alg` header**: HS256 means a local token (signed by the `auth` service with `LOCAL_JWT_SECRET`), and RS256 means an Authentik token (checked against JWKS, with audience = `AUTHENTIK_CLIENT_ID`). There is no global mode switch. Services only call `Depends(require_role("admin", "user"))` and get back a `CurrentUser(subject, role, source)`.
- `migrations.py`: the shared Alembic env logic. Each service's `migrations/env.py` just imports its models and calls `run_migrations(Base.metadata)`.
- `entrypoint.sh`: the container CMD for every backend. It runs `alembic upgrade head`, then `uvicorn`. **Schema changes happen only through migrations**, because the apps never call `create_all`.
- `__init__.py`: just `__version__` — the single source of truth for the app version, surfaced in every service's `GET /health` and OpenAPI `info.version`, and in both frontends' Settings footer (`js/version.js`, kept in sync by hand — no build step reads one from the other). Bump this, the five `pyproject.toml` `version` fields, and both `version.js` files together on a real release.

**Roles:** `admin` / `user` / `viewer`. Authentik groups map to roles via the admin-editable `admin_group`/`user_group`/`viewer_group` settings (default `household-system-{admins,users,viewers}`; see the auth service entry below) — not a hardcoded dict. **Explicit allow-list, not fail-open-to-viewer**: a validly-signed Authentik token whose `groups` claim contains none of the three configured names is rejected outright (401 from `_verify_authentik_token`), not downgraded to `viewer` — being a real user on a shared Authentik instance that also serves other homelab services is not by itself a reason to get into this one. (This was originally fail-closed-to-viewer; changed after a real homelab's Authentik instance made the gap concrete — anyone with e.g. `svc-omada-admins` or `svc-proxmox-admins` and nothing household-related could otherwise log in as a viewer.) Viewers are read-only. **Storage has no admin/user distinction at all** — deliberate, not unfinished; nothing in that domain needs gatekeeping beyond logged-in-vs-viewer. **Household gates 7 routes to admin-only** (`can_admin = require_role("admin")` in its `main.py`): weekly goal/money-rate/reminder-schedule settings, running the balancer on demand, generating/marking-paid a report, and the Authentik connection panel. Both frontends' `js/auth.js` also read this dynamically now (`warmGroupRoleMap()`, fired-and-forgotten at boot, never awaited — an unreachable auth service must not delay the first render) — renaming a group through the panel needs no frontend edit or rebuild either. This used to be a hardcoded, manually-synced mirror; that caused a real production incident (an admin's own renamed Authentik group left them stuck on `viewer` client-side, including blocked from `/admin` by the router's own guard, even though the backend was already authorizing them correctly — traced by decoding their token in the browser console and confirming the backend accepted it directly via `fetch`) before it was made dynamic.

**auth service:** local-account fallback. `POST /token` (OAuth2 form login, returns an HS256 JWT with a `role` claim; rate-limited per-username by `auth_service/rate_limit.py` after 5 failures/15min, not per-IP — see that module's docstring for why), `POST /bootstrap-admin` (unauthenticated, only works while there are no users), and `POST /users` (admin only). Also owns the live Authentik connection config: `GET /authentik-config` is public (the issuer/JWKS/client-id/group-names/etc. values aren't secret — they're already visible in every OIDC redirect), falling back to `shared/config.py`'s env-sourced defaults until an admin saves an override. This now includes `admin_group`/`user_group`/`viewer_group` (which Authentik group name maps to which app role — a hardcoded dict before this), so `shared/auth.py` no longer has a `GROUP_ROLE_MAP` constant; `_role_from_groups` reads these three the same cached-and-polled way as the other seven fields. `PUT`/`POST /authentik-config/reset` are admin-only **and** additionally require a local admin's username+password in the request body — whoever can repoint `issuer`/`jwks_url`/the group names controls who every service trusts as an admin, so a currently-valid bearer token alone isn't enough. `PUT` also rejects non-distinct group names (reusing one across two roles would make the higher one unreachable, not shared). Every service (household/storage backends, and auth itself, over its own `auth:8000` alias) polls this through `shared/auth.py`'s `_AuthentikConfigCache` (60s TTL) instead of reading `Settings` directly, so a saved change reaches token verification everywhere without a restart — **except** both frontends' `ROLE_FROM_GROUPS` in `js/auth.js`, which is still a hardcoded, manually-synced, UI-display-only mirror (never used for actual authorization) and still needs a source edit + rebuild if you rename a group and want the UI to agree with what the backend now enforces.

**storage service:**

- Backend: routes are in `main.py`, query logic in `crud.py`, Pydantic I/O models in `schemas.py`. The `/items/bulk*` routes must stay declared **before** `/items/{item_id}`, or FastAPI matches the wrong route.
- Images are stored in the `storage-images` volume at `/app/data/images`, and serving them requires auth.
- Baseline migrations are written as idempotent "create if not exists", so databases created before Alembic adopt the schema cleanly.

**household service:** the full chores/points domain from `PROJECT_SPEC.md` is built — `Task`/`TodoItem`/`PointsEntry`/`Category`, the auto-balancer (`household_service/balancing.py`'s pure `balance()`/`rebalance()`, invoked from `crud.run_balancing`), web push, PDF reports, points→money conversion. See `PROJECT_STATE.md` for the full feature-by-feature status.

- **Chained tasks**: a `Task` can declare `TaskChainLink`s — "when my occurrence is created, also spawn these onto the board as one-off `TodoItem`s." **Trigger is the parent TODO's own creation, not its completion** (`crud._spawn_chain_children_on_creation`, called from `create_todo`/`trigger_event_group` right after the parent's `assigned_to_id` is finalized) — user request: chain tasks should already exist alongside their parent, not only appear once it's done. `same_user=True` assigns the spawned todo directly to whoever the PARENT is currently assigned to (possibly nobody); `same_user=False` assigns it immediately through the same fairness logic the balancer's sweep uses (`crud._assign_chain_todo_now`, sharing `crud._gather_balancer_load` with `run_balancing`), excluding the parent's current assignee, if any — neither tries to track who ends up actually completing the parent, and reassigning/claiming/taking over the parent afterward never touches an already-spawned child (same user request, explicit: "reassignment only changes the reassigned task without touching the chain task"). `TodoItem.spawned_by_todo_id` (self-referencing FK, `ON DELETE CASCADE`) marks which parent todo's creation spawned a child, with its own `uq_todo_chain_spawn_by_todo` unique constraint alongside the older entry-keyed one — both can be null at once (an ordinary todo), never both set. `TodoItem.chain_spawn_handled` is set on the parent the moment this runs (whether it actually spawned anything or the creator opted out via the "Also create its chain task(s) now" checkbox on `POST /todos` — `TodoCreate.spawn_chain_children`, default true, shown by the frontend only when the picked task actually has an outgoing chain link) — `complete_todo`/`complete_task` still fall back to spawning AT completion (`crud._spawn_chain_children`, the older of the two — both now share the common tail `crud._spawn_one_chain_child`) for anything that was never routed through the creation-time path at all: a daily/weekly/monthly `Task` completed directly from Home (never a `TodoItem`), or a todo that predates this change (`chain_spawn_handled` still false, old data). **Cancelling a parent todo deletes its own still-open chain children with it** (`crud.cancel_todo`, a `DELETE ... WHERE spawned_by_todo_id = :id AND status = 'open'` — deliberately only open ones; a child someone already completed, or already cancelled on its own, is left alone) — `GET /todos/{id}/chain-children` (`crud.list_chain_children`) lets the frontend warn by name before confirming a cancel that would do this. A task reachable only as someone's chain child (`crud.is_chain_child`/`chain_child_task_ids`, derived live from `task_chain_links` — never a stored flag) has exactly one source of instances: excluded from `run_balancing`'s sweep, and `complete_task` rejects completing it directly (409 unless `force=True` — see below) — its points only come from completing the spawned todo. **Chaining is capped at exactly one level** — `crud.create_chain_link` rejects a new link if the proposed parent is already a chain child, if the proposed child already chains something else (`crud.is_chain_parent`), or if the proposed child is already someone's chain child. A task is a pure parent, a pure chain child, or neither — never both — which makes a chained loop structurally impossible (a cycle needs some task with both an incoming and outgoing chain edge). Multiple children per parent is still fine, only depth is capped. Get all three checks right if you touch this — an earlier version only checked two of the three and let `C→A→B` through when `A` was already `B`'s parent; caught by actually attempting it against a live DB, not by re-reading the code. Adding/removing which tasks chain a given task is still only ever done from the Tasks page's own chain-link editor — the board's checkbox only skips spawning for one todo, it's not a second place to edit the link itself.
- **Completing a chain-child task directly** (`force` on `TaskCompleteRequest`): `crud.complete_task` rejects this by default (409) unless `force=True`, which bypasses *only* that one check — everything else (the `times_per_day` cap, ramp-up, chain-spawning the task's own further children — always a no-op here in practice, since chaining is capped at one level, a chain child can never itself be a parent) still applies. The frontend only ever sends `force: true` after a confirm dialog naming which task(s) chain it (`GET /tasks/{id}/chain-parents`, the reverse of `/chain-links` — `crud.list_chain_parents`/`ChainParentOut`). Deliberately doesn't touch any already-spawned, still-open todo for the same chain link — which one(s) to cancel is ambiguous when more than one occurrence could legitimately be outstanding, so that judgment call is left to the person confirming, same as `times_per_day` already does.
- **On-break AND viewer exclusion from assignment**: `crud._check_assignable` rejects handing work to an on-break user (400) — used by todo create/update, the admin reassign, and takeover-request creation. The balancer's sweep/rebalance and the chain-task auto-assigner build their own `eligible` list via `crud._is_eligible_for_tasks` (not `_check_assignable`, since there's no single user to reject — it's filtering a whole household), which excludes both `on_break` **and** `role == "viewer"` — a viewer can never complete anything themselves (`can_write`-gated), so handing one a balancer-swept task or chain-spawned todo just leaves it permanently stuck. If `_is_eligible_for_tasks` finds nobody, the item is left unassigned, same as any other "nobody eligible" case.
- **Reassign vs. takeover request, UI clarity**: both the Board's admin-only reassign button (`icons.swap`) and the "ask to take over" button (`icons.send`, `household/frontend/js/takeover.js`) are deliberately distinct icons with explanatory tooltips — they're easy to conflate since both end with "someone else holds it now." Any writable user (not just admin) can ask to take over something THEY currently hold, from either Home or the Board (`takeover.js`'s `takeoverControl()` is shared between both pages). `household/frontend/js/taskPicker.js` (search + category-filter popup, also shared — originally board.js's "From task" picker) is what backs the Tasks page's chain-task child selector too, replacing a native `<select>` that would otherwise flood with every task in the household — **picking a task in that popup immediately performs the action** (adds the chain link / prefills the todo form, depending on caller), on purpose: an earlier two-step "pick, then press a separate Add button" version let a user pick a chain task, then press the Edit Task modal's main Save button assuming the pick was already part of what got saved — it wasn't, and nothing told them so.
- **Notification inbox**: the bell icon next to Settings in the topbar (`household/frontend/index.html`, wired from `household/frontend/js/notifications.js`) is a persistent, checkable inbox, backed by a real `Notification` table — not just the one-shot Web Push notifications this app also sends. **`crud._notify()` is the one place that creates a notification** — every notify_* function (todo assigned/reassigned, takeover requested/responded, weekly nudge, new report) goes through it, which always writes the in-app `Notification` row first, then attempts push as a best-effort bonus (returning the push-specific success count for `send_weekly_nudge`'s delivery stats). Never call `push.send_to_subscriptions` directly from a new call site — a push-only notification is invisible to anyone without a subscription, a denied permission prompt, or a browser that lost it, which is exactly the bug this replaced (an admin reassign "not showing up in the notifications window" — the push fired and silently went nowhere; nothing was ever recorded for the bell to show). The bell's badge count is incoming-takeover-requests + unread-notifications combined (`GET /notifications?unread_only=true`); the panel has a "Takeover requests" section (actionable) and a "Recent" section (dismiss = `POST /notifications/{id}/read`, ownership-checked). Polls every 30s; every page that can also resolve a takeover request (Home, the panel itself) calls `refreshNotificationBadge()` after doing so rather than waiting for the next poll. Hidden for a viewer or before login — `refreshNotificationBadge()` re-checks role on every call (not just once at boot), since local login (`login.js`) is an in-SPA `navigate()`, not a real page reload, so there's no second `main.js` boot to re-evaluate who's logged in. Visibility is toggled via the `.hidden` CSS class (`base.css`, `!important`), not the native `hidden` attribute/IDL property — `.btn`'s own `display: inline-flex` has equal specificity and wins the cascade over the browser's built-in `[hidden]` rule, so `el.hidden = true` on anything `.btn`-classed silently has no visual effect. Use `classList.toggle("hidden", ...)` for any `.btn`-classed element you need to show/hide. `renderPanelList(overlay, { initial })` only clears `#notif-panel-takeover` to a loading skeleton when `initial` is true (the panel's very first render, from `openNotificationPanel`) — every other call (after mark-all-read, accept/decline, dismiss) is a RE-render of an already-open panel that already has real content on screen; clearing it first and refilling after the refetch put a visible empty gap between the two, which read as the whole panel flickering shut and reopening. Leaving the old content in place until `renderTakeoverSection`/`renderPlainSection` swap it for the new content in one go removes that gap entirely.
- **Push has a 10s timeout** (`push.py`'s `_send_one`, the `webpush(..., timeout=10)` call) — `pywebpush`/`requests` has none by default, so one slow or unreachable push endpoint could otherwise hang the awaiting request indefinitely (reproduced live at 2+ minutes on a stale subscription). A timeout is treated as an ordinary delivery failure (caught by the existing generic exception handler), not a dead subscription — the row is kept, not deleted.
- **Admin reassign vs. takeover requests**: two different ways an assignment changes hands, both only for board `TodoItem`s (not recurring `TaskAssignment`s, except takeover requests which cover both). `POST /todos/{id}/reassign` (`can_admin`) is instant, no consent needed (`crud.reassign_todo`) — still respects a chain todo's `exclude_user_id`, and notifies the new assignee (`crud.notify_todo_reassigned` — distinct wording from a takeover request's "asked you to," since this is a done deal, not something to respond to). A takeover request (`can_write` — any writable user, not just admin) is consent-based: `TakeoverRequest` (new table, `todo_item_id`/`task_assignment_id` — exactly one set, enforced by a `CheckConstraint`; only one *pending* request per item, enforced by two partial unique indexes since a plain composite unique index can't do it — NULL-vs-NULL is never a duplicate in SQL) sits in `pending` until the target accepts or declines, or the requester cancels. `accept_takeover_request` re-validates the requester still holds the item with a conditional `UPDATE` (same race-safety pattern as `claim_todo`) before moving it, and stamps `TaskAssignment.reassigned_at` so the balancer's rebalance pass won't immediately pull an accepted assignment back. Going on break, an admin reassign, or the balancer's rebalance pass all cancel whatever pending takeover request they just made stale. `board.js`'s `iHoldIt` (whether to show the takeover-ask control on a row) must also check `todo.status === "open"` — the `.takeover-slot` element it replaces only renders inside that same open-only actions block, so without this check, holding a todo that's since been completed/cancelled (nothing clears `assigned_to` on either) crashed `replaceWith()` against an element that was never there; found live by filtering the Board to "Completed" while signed in as whoever held one.
- **Tasks-page calendar view**: a List/Calendar toggle next to the "Tasks" heading (`tasks.js`'s `renderCalendar`) — a month grid of weekly tasks placed on their scheduled weekdays, with monthly tasks called out in a separate strip above it (no specific day of the month to place them on) and daily tasks shown on **every** cell, dimmed (`.cal-day-task-daily`) so a weekly task — the one actually scheduled for that specific day — still stands out at a glance. Excludes chain-child tasks regardless of recurrence (see "Chained tasks" above) — they have no independent schedule of their own. Respects the configured week start (`GET /settings`'s `week_start_weekday`) for column order, same rotation math as Stats' heatmap but implemented independently (a one-off month grid has different padding needs — leading *and* trailing blanks — than a scrolling year of days).
- **Event Groups**: a named bundle of **root** `Task`s (`EventGroup` -> `EventGroupTask`, unique per group, ordered) that posts one open `TodoItem` per root in a single trigger, taking the existing one-level chain cap into account instead of adding a second chaining concept — a root's own `TaskChainLink`s are what actually cover the rest of the event (e.g. "Fill dishwasher" chains "Handwash cutlery"/"Empty dishwasher"; neither is itself a row in `EventGroupTask`). `EventGroupExclusion` stores which of a root's chain descendants to leave **untagged** when they spawn — exclusions, not inclusions, on purpose: inclusions would silently miss a chain link added after the group was saved, where exclusions default a new link to grouped. `EventGroupRun` is one row per trigger, so the Board can tell today's "Dinner" apart from a different day's; `TodoItem.event_group_run_id` tags both a group's own root todos and any chain descendant that inherits the tag from its parent (unless excluded). `crud.preview_event_group` is stateless (raw task ids in, not a saved group) so the same computation backs the create-modal's live preview and the pre-trigger confirmation, always walking `TaskChainLink` live rather than cached membership. **Each root's own chain children spawn in the same trigger**, right after the batch balance pass finalizes that root's `assigned_to_id` (`crud._spawn_chain_children_on_creation`, the same creation-time spawn "Chained tasks" above uses — a root's own `chain_link_id` is null, it's `source_task_id` that gets its chain links looked up) — not deferred to the root's eventual completion, same reasoning and same user request as the general chain-task change. `EventGroupTriggerResult.todos` therefore includes the spawned children too, not just the roots, so the trigger toast's count is accurate. Triggering runs the balancer's own fairness pass (`_gather_balancer_load`/`balancing.balance`) once immediately across all the batch's roots, rather than waiting for the 6-hour sweep — an event-group task is time-sensitive. A root must be active and not itself a chain child (`crud._validate_event_group_roots`, same "one source of instances" reasoning as chain tasks), re-checked fresh at trigger time, not just at save. Frontend: Tasks page gained an "Event Groups" section (`tasks.js`'s `openEventGroupModal`) whose root picker reuses `openTaskPickerModal` (pick = add, same as the chain-link editor) rather than a native multi-select. The section sits between Categories and Tasks (not below the — often long — Tasks list), with an empty-state "Create your first one" call to action. `household/frontend/js/eventGroups.js` holds `openTriggerConfirmModal(group, { onTriggered })` and `openEventGroupPickerModal({ onSelect })` — pulled out into their own module (not left as tasks.js-local functions) specifically so board.js can reuse the exact same trigger-confirmation flow; `onTriggered` is how board.js refreshes the todo list afterward, tasks.js just omits it since nothing on that page changes on a trigger. The confirm modal re-fetches the preview fresh — every row reads "Created now" (roots and chain descendants alike, since both are created in this same trigger), plus "Chained from: {root}" (lineage, not timing) and Grouped/Not-grouped for a descendant — since `showConfirmDialog` only takes a plain string. **Both pages' entry points for this moved twice now** on repeated "hard to find" feedback: Tasks page went icon-only → full-width inline button → a dedicated `.fab-secondary` (`#add-event-group-fab`), stacked right above the primary "+New task" FAB; the Board went a buried New Todo modal footer button → its own `.fab-secondary` (`#trigger-event-group-fab`, opens the picker directly, no detour through the todo form). A page using two stacked FABs also needs the `.page-dual-fab` class (extra `padding-bottom`) or the primary FAB visually covers the scrolled-to-bottom content — `.fab-secondary` sits `68px` above `.fab`'s own position so neither overlaps, and its `right` is `.fab`'s own `right` plus `4px` (half the 8px width difference between the two — 56px vs. 48px) specifically so the two buttons' CENTERS line up on the same vertical axis; at an equal `right` they're flush on one edge but visibly off-center from each other (user feedback: "not centered"), since a narrower button right-aligned the same way as a wider one necessarily has its own center shifted inward. Board's "Group by event" toggle (same chip row as the status filter, localStorage-persisted per viewer) now clusters every member of a run into one bordered `.event-card` — pulled together regardless of each member's position in the fetched list, not just a plain heading floating above flat rows (user feedback: make them "identifiable as an event that belongs together") — with a trash-icon button in the card header for bulk-deleting the whole run (see "Bulk-deleting an event group run" above); that button only exists while grouping is on, since there's no card to put it on otherwise. Every row still carries the group's name as a badge regardless of the toggle, since a chain-spawned member of the run can land far from its root in fetch order. The New Todo form's chain-task checkbox (see "Chained tasks" above) now also shows which chain task(s) it would create — `GET /tasks/{id}/chain-links`, the same fetch that decides whether to show the checkbox at all, reused for its names too — with a request-sequence counter so quickly picking task A then task B can't show A's chain names under B's checkbox.
- **Event Group scheduling**: `EventGroup.schedule_recurrence` (`"daily"`/`"weekly"`/`None` — a plain `String`, not a Postgres enum, since `MIGRATIONS.md`'s enum section makes adding/dropping a Postgres enum value its own migration dance and there's nothing here that needs one) lets a group auto-trigger instead of needing someone to tap it. `"monthly"` is deliberately not offered — unlike `Task.recurrence`, there's no "sometime this month" concept that makes sense for a trigger that creates todos immediately. `schedule_weekdays` (0=Monday..6=Sunday, only for `"weekly"`) and `schedule_hour` round it out. `household_service.scheduler`'s hourly `_event_group_tick` calls `crud.run_scheduled_event_groups_if_due`, which checks every scheduled group against the pure, independently unit-tested `crud._event_group_due(recurrence, weekdays, hour, ran_today, now, tz=...)` — an **exact** hour match (not `>=`, so saving a schedule whose hour already passed today doesn't fire immediately, and a restart hours late doesn't fire a backlog) and "already ran today" counts a **manual** trigger too (querying `EventGroupRun.triggered_at` for the household's own local calendar day, not a separate flag), so triggering by hand earlier the same day correctly suppresses tonight's automatic one. Each group is wrapped in its own try/except with `db.rollback()` on failure (e.g. a root went inactive) so one bad group can't poison the session for every other group checked in the same tick. `trigger_event_group`'s `user` param is `HouseholdUser | None` now — `None` for a scheduled auto-trigger, which is also why `TodoItem.created_by_id`/`EventGroupRun.triggered_by_id` both had to become nullable (migration `0b83dc22261d`); the frontend shows "Scheduled" in place of "by {name}" when `created_by` is null, and the notification sent gets its own "{group} created: {todo}" body (`notify_todo_assigned`'s "X asked you to" wording needs a human requester it doesn't have).
- **`HouseholdSettings.timezone`** (IANA name, e.g. `"Europe/Berlin"`, `NOT NULL` default `"UTC"` — migration `7a2baea5f6dc`): what `schedule_hour`/`schedule_weekdays` above and `nudge_hour`/`nudge_weekday` are interpreted IN, not UTC outright like they both used to assume (user report: "Time for time scheduled event groups is in UTC"). `_event_group_due`'s `tz` kwarg converts `now` to this zone via `now.astimezone(ZoneInfo(tz))` before reading `.hour`/`.weekday()` — defaults to `"UTC"` so every call site that doesn't pass it keeps the exact old behavior (every existing test still passes unmodified). `run_scheduled_event_groups_if_due`'s "already ran today" window is the household's local calendar day's own midnight-to-midnight span, converted to UTC for the query — correct across a DST shift (that local day is 23 or 25 hours long in UTC terms; this captures exactly that span, not a flat 24h window). `run_scheduled_nudge_if_due`/`send_weekly_nudge` got the same treatment, including the "which week" dedup stamp (`last_nudge_sent_week`) — both now derive it from `datetime.now(UTC).astimezone(ZoneInfo(settings.timezone)).date()`, not raw UTC, so the manual "send now" button and the scheduled tick can't disagree about which week it is right around a local midnight that falls on the other side of the UTC day boundary. Validated with `ZoneInfo(v)` in `HouseholdSettingsUpdate`'s own field validator (422 on an unrecognized name). Deliberately scoped to ONLY these two "what hour of day" pickers — `due_date` comparisons, `week_start_weekday`'s own day-boundary semantics, the balancer, and everything else stay UTC-anchored; widening that is a separate, much bigger change this wasn't asked for. Frontend: Admin panel's new "Timezone" settings block populates a `<select>` from `Intl.supportedValuesOf("timeZone")` when available (with `"UTC"` prepended — Chrome's own list omits the plain alias), falling back to a free-text input (still server-validated) otherwise; every "At (UTC)" label in both `admin.js` and `tasks.js`'s Event Group schedule picker now reads the real configured zone instead. `admin.js`'s `patchSettings` helper — the one `PUT /settings` call site, since that route replaces the whole row — had to gain `timezone: current.timezone` in its spread-defaults, the same gap `overdue_delete_after_days` had the round before: forgetting a field there means every *unrelated* Save (goal, nudge, overdue) silently resets it to the schema's own default.
- **Bulk-deleting an event group run** (Board, `.event-card`'s trash button): a REAL hard delete, not `cancel_todo`'s soft status change — the user explicitly asked for "delete," and a cancel would've just reappeared under the Cancelled/All filters. `crud._hard_delete_todos(db, todo_ids)` is the one place any hard delete goes through now — a single todo (`delete_todo`), a whole run at once (`delete_event_group_run_todos`), and the scheduled overdue cleanup below all call it. It exists because `TodoItem.spawned_by_todo_id`'s `ON DELETE CASCADE` doesn't look at status: deleting an open root would otherwise also wipe out a child that's already completed (earned real points) or already cancelled on its own. It first nulls `spawned_by_todo_id` on any non-open child of the ids being deleted (same "stays, just loses the why pointer" treatment `chain_link_id`'s own `SET NULL` already gets), then deletes. `crud._event_group_run_cleanup_candidates(db, run_id)` is every todo a bulk delete of one run would consider — todos actually tagged with the run, PLUS any chain descendant spawned by one of those that ISN'T tagged (excluded from the group's own tag via `EventGroupExclusion` — still part of "this event" for a bulk delete even though it never showed up clustered or badged for it). `event_group_run_delete_preview`/`delete_event_group_run_todos` share that candidate computation so the GET preview and the POST that actually deletes can never disagree about what's affected — the frontend's confirmation warning is built from the real server-side preview (`GET /event-group-runs/{run_id}/delete-preview`), never guessed client-side from `todosCache`, specifically so it can't miss an untagged-but-affected child. `EventGroupRunCleanup`/`TodoStubOut` is the shared `{to_delete, to_keep}` shape both the preview and the real result return.
- **Scheduled overdue cleanup**: `HouseholdSettings.overdue_delete_after_days` (`None` default = off, same opt-in pattern as the nudge schedule) — `household_service.scheduler`'s hourly `_overdue_cleanup_tick` calls `crud.run_scheduled_overdue_cleanup`, which hard-deletes (via `_hard_delete_todos` above, so a completed chain child is spared the same way) any still-open todo whose `due_date` is more than that many days in the past. "Overdue" means the same thing the Board's own due-date badge does (`util.js`'s `dueBadge`: `due_date < today`, both UTC-anchored) — this just adds days of grace before the delete, not the day it first turns overdue. No "already ran today" dedup needed, unlike the nudge/event-group ticks — the delete query is naturally idempotent, a row that's gone can't match it again. Takes an injectable `today` for the same testability reason as `_event_group_due`'s own `now`.
- **Multi-language support (English/German)**: two independent translation layers, each with its own "whose language" rule, documented in `household_service/i18n.py`'s own module docstring. (1) **Notifications** render in the RECIPIENT's `HouseholdUser.preferred_language` — every `crud._notify()` call site builds its title/body via `i18n.t(lang, key, **params)` rather than a literal string, `lang` coming from the recipient's own row (`_recipient_language()` helper, or a direct `.preferred_language` read where the caller already has the right object loaded). (2) **PDF reports** (`reports.py`) render in the household's shared `HouseholdSettings.default_language` instead — one document, not per-viewer, so it can't follow each admin's own preference; `generate_report_pdf`'s `lang` param also drives German-idiomatic date (`06.10.2026` not `06 Oct 2026`) and decimal-comma (`12,50 EUR`) formatting, not just string lookups. `HouseholdUser.preferred_language` (default `"en"`) is seeded once, at row creation (`crud.get_or_create_household_user`), from the admin-configured `HouseholdSettings.default_language` — changing the admin default afterward is deliberately **not retroactive**, only `PATCH /me/language` (`can_read`-gated, so a viewer can set their own language even though the broader `PATCH /me` is `can_write`-gated) changes an existing user's language from then on. `admin.js`'s `patchSettings` had to gain `default_language: current.default_language` in its spread-defaults — the same gap `overdue_delete_after_days`/`timezone` each had their own round before, since `PUT /settings` replaces the whole row. Frontend: `household/frontend/js/i18n.js` is the parallel client-side layer — `en.js`/`de.js` are static ES-module imports (not fetched), so a locale is synchronously resolved, `<html lang>` is set, and `localStorage`'s cached value is read before ANY other module's own top-level code runs; `t(key, params)` falls back de → en → the raw key itself (never silently blank, matching the backend's own "fail loud on a typo" reasoning), and a value may be a plain string or a `{one, other}` plural form selected via `Intl.PluralRules` against `params.count`. The cached locale is reconciled against the server's real value once per boot (`syncLocaleFromServer`, unawaited — same "don't let an unreachable backend delay the first render" reasoning as `auth.js`'s `warmGroupRoleMap`) and again right after a LOCAL login (`login.js` calls it directly, since local login is an in-SPA `navigate()`, not a real second boot) — a mismatch reloads the page once (session-guarded against a reload loop), since there's no in-place re-render system for a language change. Changing language from Settings itself works the same way: `PATCH /me/language` → `setLocale()` → `window.location.reload()`. Two deliberate, documented gaps: backend `ValueError`/`HTTPException` `detail` messages stay English-only (would need real error codes, a bigger change), and the storage frontend wasn't touched at all (no admin/settings concept to hook a default language into — see "Storage has no admin/user distinction at all" above).

- **Always-assign (pinned) tasks**: `Task.pinned_user_id` — a standing household agreement ("Alex always does the bathroom"), not a fairness decision. Lives entirely inside `household_service/balancing.py`'s pure functions, not as a crud-level special case, specifically so it's covered by `test_balancing.py` the same way everything else there is: `CandidateTask`/`CandidateTodo.pinned_user_id` makes `balance()` hand that item straight to its owner (bypassing both the fairness pick AND the per-run cap — it's never a "new fairness-allocated item" to begin with) if they're currently eligible, or leave it unassigned otherwise — **never** handed to anyone else just because the pinned person is on break; that would defeat the whole point. `rebalance()` skips any `PullableAssignment` with `pinned=True` unconditionally. A THIRD, separate pure function, `correct_pins()`, handles the case an existing `TaskAssignment` is held by the wrong person (the pin was just set, or changed, after this period's assignment already happened) — moves it back to the pinned owner, gated on `has_progress`/`already_reassigned` (sourced from the SAME `TaskAssignment.reassigned_at` column `rebalance()`'s own pull stamps, but ALSO stamped by `crud.accept_takeover_request`'s consent-based move — critical: a pin correction must never silently undo someone's own accepted takeover, and there's no way to tell the two apart from that column alone, so both are treated identically). `crud.run_balancing` wires all three in: `correct_pins()` runs first (before the sweep, so its load/count effects are reflected for the rest of that run), then pinned tasks flow through the SAME `candidate_tasks`/`balance()` call as everything else (just with `pinned_user_id` set, from `task.pinned_user_id`), then `rebalance()`'s own pullable list sets `pinned=task.pinned_user_id is not None` per assignment. **Scope, deliberately**: covers `run_balancing`'s weekly/monthly task sweep, `run_balancing`'s unclaimed-board-todo sweep (`CandidateTodo.pinned_user_id` resolved from the todo's own `source_task_id`, via a small targeted query — a todo has no pin of its own), and `trigger_event_group`'s batch balance (resolved from each root's own `task.pinned_user_id`, paired back to its spawned todo via `zip(created, group.roots)` since both lists are built in lockstep). Does **not** cover `_assign_chain_todo_now` (a chain-spawned todo's own child task) — moot in practice, since pinning a chain-child task is already structurally inert (see below) — nor `claim_todo` (an explicit human action is left as a deliberate override, not a fairness decision to gate). **Applies to every recurrence except a chain-child task** (as of the `manual`-recurrence round below — originally restricted to weekly/monthly, with `daily` auto-cleared; that restriction was lifted on explicit request). For `daily`/`manual`, where the balancer never runs at all, a pin has a narrower, deliberately-scoped meaning: it shows as an informational badge and still routes any TodoItem actually CREATED from that task (an Event Group root, a Board "From task" post left as "Anyone") to the pinned person — via the exact same `CandidateTodo.pinned_user_id` path a weekly/monthly task's spawned todos already use, so no extra code was needed for this part — but does **not** restrict who can complete a `daily` task directly from Home; that's an offered-not-built follow-up, not silently decided. Naturally inert for a chain-child task — the sweep's existing `excluded_chain_child_ids` filter already skips those before any pin logic runs — and **not** auto-cleared server-side the way `recurrence` becoming `daily` used to be, since chain-child status is derived/dynamic (from `task_chain_links`, can change at any time a link is added/removed), not a stored column; the frontend just hides the picker whenever `is_chain_child` is true. **Admin-only to set or change** (`main.create_task`/`patch_task`, checking `"pinned_user_id" in data.model_fields_set` and that the value actually differs from the task's current one before requiring `user.role == "admin"`) — unlike every other task field, which is an ordinary `can_write` edit: pinning bypasses both the fairness algorithm and the consent-based takeover-request design, the same reasoning that makes the Board's own admin-only reassign distinct from the consent-based takeover request any writable user can ask for. `TaskUpdate.pinned_user_id` needed `model_fields_set` rather than the `is not None` pattern every other `TaskUpdate` field uses — explicit `null` must be able to clear an existing pin, while omitting the field must leave it alone, and the ordinary pattern can set a value but can never explicitly clear one back to `null`. `HouseholdUserOut` gained a `role` field (previously only on the current user's own decoded JWT, never exposed for anyone else) specifically so the frontend's pinned-owner picker can exclude viewers client-side the same way `crud._validate_pinned_user` already would reject one server-side — not secret information, household members already know each other's roles. Frontend: Tasks page's task-edit modal gained an "Always assign to" select, visible to everyone but only enabled for an admin (`isAdmin()`), hidden only when the task `is_chain_child`; the task list row gained a badge (`"Always: {name}"`) when `pinned_user_id` is set. The form always sends `pinned_user_id` (explicit `null` for "No one"), since the PATCH route's clearing logic depends on the field being present in the request body, not just non-null. Board's New Todo form also prefills "Request from" with a picked task's pinned owner (if they're assignable) — purely a convenience, since left on "Anyone" it'd still reach them eventually via the balancer's sweep after `CLAIM_WINDOW`, just with a visible delay that looks broken in the meantime.

- **Manual (non-repeating) tasks**: `Recurrence.manual` — a task with no automatic occurrence of its own at all, unlike every other recurrence (`daily` is ad-hoc-completable from Home anytime; `weekly`/`monthly` get auto-swept into a `TaskAssignment`). The only way an instance of a `manual` task is ever created is a deliberate action: an Event Group trigger, a chain spawn, or someone picking it from the Board's "From task" picker — exists specifically for a task that's really only meaningful as an Event Group root or a chain link, where `daily` (confusingly ad-hoc-completable on top of whatever the group/chain does) or `weekly`/`monthly` (auto-swept into a REAL `TaskAssignment` on top of whatever the group/chain creates) would be actively wrong, not just unused. `crud.complete_task` rejects completing one directly with a 409 and **no** `force` override (unlike the chain-child rejection it sits next to — there's no legacy data to stay permissive for; `manual` is a brand new recurrence) — always completed via whichever todo it was posted/spawned/triggered as instead (`crud.complete_todo`, which stamps the represented task onto the `PointsEntry` independently and never calls `complete_task` at all). **`Task.recurrence` converted from a Postgres enum to a plain `String`** to add this value (migration `a74f9c9fa5ed`, hand-written — autogenerate's version omitted the `USING recurrence::text` cast an enum-to-varchar change needs, and left the column's default still referencing the enum type) — same precedent `EventGroup.schedule_recurrence` already set, and the exact reasoning MIGRATIONS.md's enum section documents: adding a Postgres enum VALUE needs `ALTER TYPE ... ADD VALUE`, its own dance, not worth it for a column that already went through that dance once. `Recurrence` itself is unchanged in Python — still a normal `(str, Enum)` class, so every existing `task.recurrence == Recurrence.weekly`-style comparison in `crud.py` kept working with zero changes; empirically verified live (not just assumed) that assigning a `Recurrence` member into the now-plain-`String` column stores its correct underlying value (`"weekly"`, not `"Recurrence.weekly"` — a real Python 3.11+ gotcha for mixed-in str enums' `__str__`, which this sidesteps because SQLAlchemy's bind path never calls `str()` on the value, confirmed with a scratch ORM write against the real container before trusting it). **The sweep's own filter was the one place this could have silently broken**: it used to read `Task.recurrence != Recurrence.daily`, which would have let `manual` through too — `_task_period`'s weekly-or-else-monthly fallback would then have wrongly treated every `manual` task as monthly and handed it a real `TaskAssignment`, exactly the "automatically created" behavior this recurrence exists to NOT have. Changed to an explicit `Task.recurrence.in_([Recurrence.weekly, Recurrence.monthly])` allow-list instead of patching the exclusion further — caught in review before it shipped, not live. Frontend: `home.js` filters `recurrence !== "manual"` out of its own "All tasks" list CLIENT-side (not server-side — the Board's "From task" picker, the Event Group root picker, and the chain-link picker all reuse the exact same `GET /tasks` endpoint and still need `manual` tasks included); the Tasks-page calendar view already excludes them for free, since a `manual` task matches none of the daily/weekly/monthly filters that build its three display lists. `tasks.js`'s recurrence `<select>` gained a fourth option; `scheduleLabel()` gained an explicit `manual` case rather than falling through to "Every day."

## Frontend conventions (`storage/frontend`, and future `household/frontend`)

- Vanilla HTML/CSS/JS with native ES modules and **no build step or framework**. This is a deliberate project goal: keep it maintainable by someone who isn't primarily a web developer. It's served by nginx.
- Clean path-based routing lives in `js/router.js` (`/overview`, `/settings`, `/login`, etc.) — `history.pushState`/`replaceState` + a `popstate` listener, plus a document-level click interceptor that turns a click on an internal `<a href="/...">` into client-side navigation instead of a full page load. nginx's existing SPA fallback (`try_files $uri $uri/ /index.html;`) serves `index.html` for every route on a direct load/refresh. Both `index.html` files load their CSS/JS via root-absolute paths (`/css/...`, `/js/main.js`) specifically so this keeps working from a deep route, not just `/`.
- `js/config.js` holds the backend base URLs. In production they are the same-origin `/api/auth` and `/api/storage` paths, proxied by Caddy, which strips the prefix. During local dev they currently point straight at `127.0.0.1:8001`/`8003`.
- All API calls go through `js/api.js`. It attaches the bearer token, retries once after an Authentik refresh-token exchange on a 401, and shows toasts on errors. Images have to load through `fetchImageUrl()` (a blob URL), because `<img src>` can't send an auth header. Call `invalidateImageUrl()` after a re-upload.
- `js/auth.js` handles Authentik OIDC (Authorization Code + PKCE, public client) plus local login. For UI role gating, use `getCurrentUserInfo()`, not `decodeToken().role`: Authentik tokens carry `groups`, not `role`.
- Use `confirmDialog.js` instead of native `confirm()`.
- Theming uses CSS custom properties in `css/tokens.css` plus the `THEMES` registry in `js/theme.js`.
- **Household frontend only** (storage frontend has no i18n layer — see "Multi-language support" above): every user-facing string goes through `js/i18n.js`'s `t("namespace.key", params)` — no hardcoded English in a template literal, `aria-label`/`title`/`placeholder` attribute, or `showToast`/`showConfirmDialog` call. Add a key to `js/locales/en.js` AND `js/locales/de.js` in the same edit (nothing enforces parity automatically on the frontend the way `household/backend/tests/test_i18n.py` does for the backend's own `i18n.py`); watch for a loop/callback parameter literally named `t`, which silently shadows the imported translate function within that scope.
